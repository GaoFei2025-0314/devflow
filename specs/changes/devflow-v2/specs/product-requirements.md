## 1. 产品定位与用户

### 1.1 产品定义

Devflow是一套由AI编程助手读取、解释并执行的开发工作流技能包。V2.0通过统一任务阶段、授权边界、技能选择、验证证据和交付标准，让助手在明确范围内持续完成工作，同时减少无关流程、重复读取、重复确认和无理由的重复验证。

产品形态继续采用Markdown、SKILL.md、必要的参考资料、适配说明和维护校验工具。文件、终端、浏览器、子代理及Git等执行能力由宿主提供。Devflow不能自行覆盖宿主权限、创造不存在的工具或保证模型绝不偏离指令；合规表现必须通过可观察行为验收。

### 1.2 主要用户与需求

| 用户 / 角色 | 主要需求 | 成功表现 |
| --- | --- | --- |
| 个人开发者、产品负责人 | 用自然语言说明目标，知道进度、结果和需要自己决定的事项 | 明确范围内持续推进；能理解验证目的；能按说明验收 |
| 有一定代码知识的维护者 | 适配项目技术栈、风险政策和交付惯例 | 不混包管理器、不违反项目Git规则；变更有证据 |
| 主代理 / 控制器 | 正确选择阶段、技能和执行模式，协调任务 | 不重做已完成决策；不把局部阻塞扩展到全部任务 |
| 聚焦执行者 / 审查者 | 获得足够且准确的任务上下文 | 不重新启动全局需求流程；返回可核实结果 |
| 技能包维护者 | 知道哪些规则有效、何处有冲突、升级是否兼容 | 来源可识别；安装引用可验证；行为回归可复现 |

### 1.3 核心产品体验

用户说“先写Spec，不改代码”，最终应收到可审阅的Spec；说“按已批准计划完成实现”，助手应在授权范围内执行至工作包完成；说“解释测试在做什么”，应收到通俗、与风险对应的说明。

减少流程成本必须以任务范围、必要验证和风险边界不退化为前提。只输出更少文字、少做检查或提前宣称完成，不构成产品改善。

## 3. 目标、范围与优先级

### 3.1 V2.0产品目标

| 目标 | 要达到的行为 | 验证方式 |
| --- | --- | --- |
| G01 范围正确 | 交付用户当前要求的产物；不自动跨入未授权阶段 | 阶段与授权场景 |
| G02 工作连续 | 已授权、明确且可逆的工作持续推进；只阻塞必要依赖 | 已授权实施与局部阻塞场景 |
| G03 验证适当 | 选必要检查，复用仍有效证据，失败如实处理 | 检查选择、失效与复验场景 |
| G04 结果可验收 | 用户知道做了什么、怎么验证、哪些未完成 | 用户验收与缺陷同步场景 |
| G05 能力适配 | 使用实际工具和项目命令；安装后资源完整 | 宿主组合、包管理器与安装测试 |
| G06 可持续维护 | 来源、版本、事件和行为评估可追溯，保留兼容入口 | 统计、结构、迁移与评估检查 |

### 3.2 V2.0必须包含

所有标为P0或P1的FR需求及全部NF需求属于V2.0交付范围。

- **P0**：阶段与授权、交付政策、验证策略与有效证据、可理解的完成和验收说明。
- **P1**：角色分流与恢复、来源身份、宿主和命令适配、安装完整性、旧入口兼容、可选本地记录与行为评估。

P0/P1表示实现顺序和缺陷处理优先级，不表示P1可以在宣称“V2.0完整交付”时遗漏。若缩小范围，需要形成新的明确版本范围并重新评审。

### 3.3 后续候选（P2，不阻塞V2.0）

- 大规模重组目录或进一步减少技能数量。
- 完整解析Antigravity、Trae等未验证专有历史格式。
- 独立可视化统计仪表盘、长期自动化监控。
- 针对每个语言栈增加大量领域规则或自动安装集成。
- 基于真实长期数据进行任务收益归因、自动推荐删除技能。

### 3.4 非目标

V2.0不新增独立Agent运行时、云端服务、账户系统、收费系统、业务数据库或强制遥测；不替宿主实施操作系统权限控制；不承诺消除所有模型错误；不以固定技能数量、固定少跑测试次数或消息更短作为单独成功标准。

本Spec不授权修复本机安装、不修改项目业务代码，也不创建定时统计任务。

## 4. 用户旅程与阶段模型

### 4.1 典型用户旅程

| 旅程 | 用户输入示例 | 产品应执行 | 当前请求的交付终态 |
| --- | --- | --- | --- |
| J01 理解项目 | “先讲清楚项目做什么” | 只读定位说明、入口和核心行为，引用事实 | 解释完成 |
| J02 分析与规划 | “根据使用记录给方案 / 写Spec” | 分析已有证据、说明限制、写用户指定文档 | 本地文档可审阅 |
| J03 小改动 | “修改这段文案 / 修复这个明确Bug” | 判断影响与授权，选快速路线和适用验证 | 改动及适用证据齐备 |
| J04 已批准实施 | “按这个计划完成整个工作包” | 复用计划，按依赖推进实现、验证、审查 | 工作包完成；外部动作按授权处理 |
| J05 调试 | “这个行为不对，先定位原因” | 复现、假设、根因调查；仅定位时不擅自修复 | 根因与证据，或授权的修复结果 |
| J06 UI / 用户验收 | “调整这个界面并给我验收” | 服从设计系统，验证布局与交互，提供验收步骤 | 用户可操作的验收材料 |
| J07 交付 | “开PR / 合并 / 发布” | 匹配动作授权和项目门禁，准备可审结果再执行许可动作 | 有证据的交付状态 |
| J08 恢复任务 | “继续上次的工作” | 恢复范围、阶段、授权和证据；核对相关变化 | 从有效状态继续，不重新发起全部流程 |

### 4.2 阶段与动作分开表达

阶段用于描述正在做的工作，不自动授予动作权限。

| 阶段 | 典型活动 | 合法结束条件 |
| --- | --- | --- |
| Understand | 项目解释、只读调查、代码/记录分析 | 问题得到回答，证据与限制明确 |
| Specify | 需求澄清、产品Spec、设计或任务计划 | 用户要求的文档可审阅 |
| Implement | 已授权的代码/规则修改、适用测试 | 当前实现范围满足要求 |
| VerifyReview | 自动/手工验证、代码审查、问题修正 | 必需证据和审查结论齐备 |
| Deliver | 本地结果、PR、合并、部署或安装切换 | 已授权交付动作完成或明确等待特定授权 |

`文档就绪`、`实现完成`、`验证通过`、`待用户验收`、`待动作授权`、`已交付`是不同结果状态。阻塞是附着在任务或依赖项上的状态，不是将整个项目一律停下的理由。

```mermaid
flowchart LR
    A[识别交付物与授权] --> B[理解或规格]
    B --> C[本地文档交付]
    A --> D[已授权实现]
    D --> E[必要验证与审查]
    E --> F[当前工作包结果]
    F --> G[匹配授权的外部交付]
```

图中路径由用户请求决定；文档交付没有自动指向实施的边。

## 5. 功能需求

### 5.1 任务识别与最小路线

#### FR-01 · P0 · 识别当前交付物和允许阶段

助手必须在选择执行路线前，从当前请求、明确的历史授权和项目规则识别目标、交付物、允许修改范围及结束条件。用户中途提问、纠正或补充约束时，应更新受影响部分并保留原任务目标；只有明确取消或不兼容的新目标才替换原任务。

无法判断的高影响决策不得猜测；可通过只读事实解决的事项应先调查。无需向用户展示内部字段表，只需简明说明当前阶段和主要动作。

#### FR-02 · P0 · 覆盖只读、文档、实现和领域任务

路线必须覆盖项目解释、记录调查、仅Spec/计划、小改动、新功能、调试、评审、UI、API、安全、性能、迁移、文档和交付。先按交付物和影响面选择流程，再补领域技能。

不得仅凭“源码”“UI”“规划”等词加载不适用技能。没有框架/API语义问题的项目说明不强制加载source-driven-development；已有明确需求的实现不重新启动需求访谈。

#### FR-03 · P0 · 仅文档请求交付文档即止

当用户要求仅分析、Spec、设计或计划时，交付范围限于所要求的分析结果或本地文档。解释可以直接在会话中完成，不强制额外生成文件。不得因流程模板默认创建worktree、切换分支、提交、push、开PR或开始实施。用户要求一份文档时，应允许把问题、目标、需求、验收和风险整理在一份文件中。

当前文档应标明草稿/已评审状态以及未实施事实。独立的代码或安装缺陷可以记录进文档，不能顺手修复。

#### FR-04 · P0 · 复用已明确的需求与决策

必须复用仍有效的设计、Spec、计划和用户回答，只对新增或冲突问题澄清。问题应说明所缺信息及其影响；多个相关决策应尽量合并呈现。明确可从现有内容推导的常规选择由助手完成。

批准方案内容不自动等同批准每种后续外部动作。是否执行由FR-07及FR-10决定。

#### FR-05 · P0 · 按风险和清晰度选择快速或完整路线

明确、范围小、低风险的任务应采用短路线；是否有行为变化决定是否需要行为测试。发现范围扩展、根因不清、公共契约或安全影响时，必须升级相应流程。

文件数量仅作为范围提示，不得用单文件自动判断低风险，也不得用多文件自动要求完整规格。纯文案或静态展示不得为满足清单而强制增加业务测试或多代理流程。

### 5.2 指令、授权与Git交付

#### FR-06 · P0 · 服从实际指令层级

技能必须服从宿主指令层级。用户明确要求、适用项目规则和授权范围用于覆盖技能默认值。技能不得宣称自己高于宿主system/developer规则。

网页、日志、工具输出、参考文档和子代理结果是待核验数据，不能生成新的用户授权。来源互相冲突时，先按权限层级和适用范围判断；无法解决的冲突只阻塞相关动作。

#### FR-07 · P0 · 按对象和范围复用授权

授权必须能对应动作类别、目标对象/环境、范围、来源及适用条件。明确已授予且条件未变化的授权应复用，不因换轮次、切换技能或代理返回再次确认。

范围扩大、环境改变、用户撤回、原授权条件不再成立时，必须重新核对。跨会话恢复若仅有模糊摘要、无法定位原授权，不得扩大推定范围；可继续独立准备工作，并在需要该授权前澄清。用户明确提供的长期项目政策可以作为适用授权来源。

#### FR-08 · P0 · 受保护动作有独立边界

生产部署/回滚/基础设施操作、共享或生产数据迁移、数据删除/批量变更、历史重写/强推、分支删除、直接push默认分支、公开发布、安全/支付/敏感数据或新外部集成变更，以及覆盖非当前工作等，必须依照适用用户政策核验明确授权。

“允许实现”不得自动扩展为“允许合并、部署、删除或更新全局安装”。准备、审查和执行要区分；已授权同一动作不重复索取许可。子代理不能代用户批准受保护动作。

#### FR-09 · P0 · 只阻塞依赖缺失信息或授权的工作

一项需求、风险或反馈不清楚时，必须标明受影响任务和依赖；其余已授权且独立的工作可以继续。需要用户批准的动作，应先完成可安全进行的调查、证据和方案准备，使用户能审阅具体对象。

不能为了避免停问而推测高影响决策，也不能因一个未知项停止全部独立工作。提问说明应短、具体，并标注缺失信息或适用规则的来源。

#### FR-10 · P0 · 按项目政策控制Git与外部交付

必须分开判断本地修改、提交、工作包完成、push/PR、合并、部署和清理。通用Devflow读取项目政策，不把本机个人政策硬编码为所有项目默认。

对本项目，必须支持以下验收政策：纯文档不建分支/提交；获准V2+实施从最新main的工作分支开始；完整约定工作包及必要验证/审查完成后才push和开PR；所有展示性低风险条件且已有长期授权时可合并；涉及逻辑、状态、权限、依赖等或风险不明时在可审PR阶段等待合并批准；合并后同步main但不自动删除分支。

PR必须描述问题与结果、完整范围、风险、验证命令及结果、UI证据（如适用）、API/数据影响和残余风险。不得绕过必要CI、分支保护或把局部增量伪装为已完成版本。

#### FR-11 · P1 · 公共规则有唯一规范来源

阶段、授权、证据、交付和能力降级规则必须有可识别的规范来源。各技能、入口摘要和平台说明引用或经过一致性检查，不得保留互相冲突的固定流程。

实现可选择生成摘要或静态一致性校验；本需求不强制引入配置引擎。领域规则仍需保留有用的风险判断，不能为缩短文本删掉实质约束。

### 5.3 验证策略与证据

#### FR-12 · P0 · 先判断影响，再选择检查

必须根据改变的行为、依赖边界、风险和项目门禁确定检查范围。解释每项主要检查要防止的风险，以及为何需要聚焦、相关回归或更广范围。

纯文档采用适用的内容/链接检查；UI采用必要构建、类型、浏览器和视觉验证；逻辑Bug采用回归与相关检查；公共API、依赖、构建、安全或发布候选扩大必要验证。不默认每轮全量，也不省略项目规定的必需检查。

#### FR-13 · P0 · 保留有效的行为回归证明

对适用的行为改动或Bug，必须先获得能够说明预期差异的测试或复现证据，再做最小修复并验证。已有准确复现的测试可以复用；不得复制同义测试只为满足“新测试”字面要求。

测试失败必须是预期行为缺失/错误导致，不能把环境错误当回归成立。纯静态内容、不适用自动测试的场景应明确适用性与替代证据。不得用实现细节镜像、跳过测试或只声称手测替代项目必要验证。

#### FR-14 · P0 · 验证结果必须关联真实证据

检查记录必须区分计划、运行中、通过、失败、未运行、阻塞和不适用，并关联检查对象、范围、环境、实际结果及来源。异步工具返回“运行中”不得当作成功；必须使用对应续接结果。

代理自报、技能示例、历史摘要或“看起来正确”不能单独证明当前代码通过。人工验收和自动化检查分别记录；未做的项目不得被写成通过。

#### FR-15 · P0 · 根据相关状态判断证据有效期

证据的有效性必须由验证对象及相关状态决定，不由消息编号或是否刚提交决定。相关代码、未提交改动、参与运行的未追踪文件、锁文件、配置、测试数据、运行环境及外部状态变化需要评估影响。

仅Git HEAD一致不足以证明状态一致。相关状态未变、无新失败/疑点且原证据覆盖本次声明时应复用；发生相关变化时只使受影响证据失效并补足检查。外部环境敏感检查按其有效窗口处理；无法判断有效性时如实标记并核验。

#### FR-16 · P0 · 失败、重试和警告透明处理

必需检查失败必须阻止对应的完成/合并/发布结论；优先分析失败原因，不得隐藏失败、无限复跑直到偶然通过。重跑需要记录原因和结果，失败后通过的完整过程应保留。

疑似环境竞争或不稳定测试未定位时，不得宣称根因已修复。可以按项目政策报告残余风险和继续不受影响的工作，但不能绕过必需门禁。旧warning和新增warning区分，既不隐藏新增问题，也不将无关旧问题自动扩大为本任务范围。

### 5.4 完成、用户验收与评审

#### FR-17 · P0 · 完成状态对应当前交付物

必须分别表达文档就绪、实现完成、自动检查通过、待人工验收、待动作授权和最终交付。仅Spec请求完成时不因尚未实施而误报“任务未完成”；实施工作仍有必需功能、验证或审查未完成时不能称版本完成。

交付说明必须列出已完成范围、必要证据、未完成/暂缓/演示内容及其原因。已获用户接受的暂缓项要保留记录，不能悄悄改成通过。

#### FR-18 · P0 · 提供用户能执行的验收说明

需要人工验收的交付必须包括版本/产物、环境与前置条件、功能入口、操作步骤、预期结果、异常判定，以及占位或尚不可验收范围。措辞应适合用户的技术水平。

自动化测试数量不能替代用户操作说明。若验收涉及付费、外发或不可逆动作，应在执行前说明条件并按授权处理；默认提供可安全完成的验证步骤。

#### FR-19 · P0 · 缺陷有一致身份和事实来源

同一缺陷必须有稳定ID、问题描述、复现、影响、状态、相关版本、验证结果和证据定位。优先沿用项目已有台账；体验清单或发布视图引用同一ID或经明确同步核对。

用户追问记录状态时，应先查事实，不得把“主台账已有但视图未同步”误说为完全漏记。若项目确需多份文件，交付前核对相关缺陷ID和状态一致；无重复系统必要时不强建第二套台账。

#### FR-20 · P0 · UI同时满足工程与体验验收

已有项目先遵循设计系统和用户已选方向；重大视觉变更需先明确方向、关键布局及用户操作预期。不能将代码质量或功能测试通过等同于视觉体验通过。

实际验证应覆盖相关布局、响应式、交互、可访问性及视觉证据。简单展示改动不强制重新设计全站；没有相应运行证据时说明缺口，不伪造截图或声称体验已通过。

#### FR-21 · P0 · 评审有范围、基线和可验证结论

评审必须给出目标范围与适用基线，区分规格符合性、正确性、必要的安全/性能/可维护性问题及可选建议。发现必须能定位、解释影响，并提出可执行修正方向。

发起和接收评审复用同一标准；已有有效验证可引用。重要跨边界变更按项目规则保留独立审查；宿主无代理时明确采用自审，不能伪称独立评审。无依据的风格偏好不应阻塞完整交付。

### 5.5 技能身份、加载与恢复

#### FR-22 · P1 · 明确加载的是哪份技能

必须识别技能规范ID、实际来源路径、bundle来源及可得的版本/内容身份。同名Devflow与Superpowers等共存时，依据用户指定来源或项目规则选择；不得静默混用控制规则、覆盖其他来源或把名称相同当内容相同。

历史版本或内容身份不可得时记录未知，不倒推当前哈希为历史哈希。别名应指向唯一规范入口，不形成第二套冲突正文。

#### FR-23 · P1 · 只加载必要内容并识别截断

必须先确定当前路线和必要领域规则，再读取必要入口与引用；不默认加载全部33技能。已在当前上下文且仍有效的内容可以复用。

必须区分元数据发现、部分读取、完整读取和上下文复用。读取被截断时，应补齐当前决策所需的关键规则后再执行依赖动作；不得将80/97行称为全文已读。大段示例可以按需加载，但不能以压缩为由漏掉适用边界。

#### FR-24 · P1 · 压缩和交接后恢复有效状态

恢复信息至少包含目标/交付物、当前阶段、范围与授权来源、所用技能身份、相关验证证据、未完成项和阻塞。恢复时核对用户新指示、项目及规则变化，再选择继续或按需补读。

上下文压缩后所需规则丢失是合理补读原因；不得假装记得未保留细节，也不得为恢复一条规则重启整套需求流程。授权摘要无法核实的限制按FR-07处理。

#### FR-25 · P1 · 领域能力共享公共合同

33项现有能力必须使用一致的阶段、授权、验证和交付规则。计划、规格、执行、审查等重叠模块可以共享控制段，但应保留不同交付物和适用情形。

小任务允许轻量记录，复杂或跨会话任务提供足够持久信息。不能为了统一格式强制每项小任务生成多份文档，或为了省略文档丢失必要范围与验收。

### 5.6 宿主能力、项目命令与安装

#### FR-26 · P1 · 按实际可调用能力选择工具

必须使用当前宿主暴露的真实工具及参数，并核对文件、Shell、浏览器、子代理、Git/PR等任务所需能力。产品名或静态映射不能作为某个API必然存在的证据。

缺少能力时采用可行的降级路径并说明验证边界。不因技能示例需要而自行安装插件、改认证配置或新增外部集成。工具可用性变化时使相关适配选择失效。

#### FR-27 · P1 · 服从项目包管理器和脚本

必须依据项目规则、有效锁文件、packageManager和实际脚本选择命令，不混用包管理器。既定项目约定优先；没有约定时遵循用户偏好，当前用户的JS/TS项目默认pnpm。

多个冲突锁文件或命令无法确定时先查项目文档和历史；无法可靠解决才澄清，并继续不依赖答案的调查。Python、Rust等使用其项目实际入口，不强套Web示例。不得仅为技能示例生成第二个锁文件。

#### FR-28 · P1 · 浏览器降级不混淆验证范围

没有某个DevTools MCP时，应判断是否已有其他适用浏览器能力。存在合适工具时使用它验证；确实没有时执行可用检查并标明缺少的交互/视觉证据。

测试运行器结果不能自动替代未执行的浏览器/真机验收。若缺少的证据是当前交付必需项，应保持待验收/阻塞状态，不能通过降级把必需项取消。

#### FR-29 · P1 · 安装后的引用完整

所有声明支持的安装形态必须能解析当前技能的必要公共合同、模板和参考资料。至少验证整包安装、独立技能及其声明依赖集合复制、软链接三种形态。

“独立技能复制”应提供完整依赖闭包或明确安装依赖清单，不把仓库外隐式路径当必备资源。校验必须面向安装产物而非只查仓库；重现并防止全局project-overrides模板缺失。校验失败要准确指出缺失对象，不能仅凭入口哈希一致宣称安装完整。

#### FR-30 · P1 · 支持等级与实际证据一致

必须公开区分“当前宿主已实测”“受控能力契约验证”“仅格式兼容说明”“未验证”。V2.0首要实测目标为本机Windows Codex；Cursor覆盖实际读取/截断行为；Claude覆盖技能格式、入口解析及受控场景。

没有真实运行机会的宿主只能标受控验证或未验证，不宣称完整原生支持。其他宿主专有历史解析不是V2.0必需项。若用户后续要求某宿主完整实测，应成为显式新增的发布门槛。

### 5.7 执行模式与代理协作

#### FR-31 · P1 · 代理选择由任务条件决定

只有在用户/宿主允许、工具可用、存在可独立验证的子任务、上下文足够且无共享写入冲突时，才选择适当的代理模式。单纯“有spawn工具”不是充分理由。

小而清晰的任务可在本会话执行；紧耦合任务采用会话或串行方式。独立调查可以并行，涉及共享接口/文件时先划清边界。若存在用户成本或并发约束必须遵守，不能以提速推定额外资源授权。

#### FR-32 · P1 · 聚焦代理继承边界并返回证据

控制器必须提供任务目标、范围、必要上下文、验收项、允许/禁止动作、技能来源和返回要求。聚焦执行者不重新发起完整需求与全局路由，不得扩大范围或替用户批准。

返回结果必须包含实际完成项、文件/差异或其他定位、验证证据、缺口与阻塞。控制器核验后集成；代理自报不能单独替代集成验证。小任务可合并规格与质量检查，风险任务保留需要的独立审查。

### 5.8 可观察性与产品维护

#### FR-33 · P1 · 提供可选的最小本地记录

必须定义并支持本地导出最小任务/技能/授权/验证事件记录，或从已有宿主记录提取同等信息。记录默认关闭，不启用仍可正常完成核心开发流程。

启用时明确范围、输出位置和关闭方式；不要求常驻服务、云端账户或全量聊天复制。每次执行仍可在会话中保留必要证据，不依赖可选统计文件存在。

此开关约束Devflow新增的持续采集，不修改宿主自身的会话日志设置。按用户请求分析已有宿主记录时，同样执行最小化和来源限制，不能把一次分析扩展为持续监控。

#### FR-34 · P1 · 统计区分不同证据层级

统计必须分别表达发现/注入、用户点名、助手选择、读取请求、部分/完整正文返回、上下文复用、实际遵循和任务结果。按任务/主任务树/代理/轮次/调用分别计量，去除可识别备份、恢复和同次调用多处存储重复。

纯写文档中引用技能路径、同名上游技能、SSH主机同名、运行中未返回、未知二进制或缺失转录不得误记为成功使用或零使用。报告必须写分母、时间范围、来源版本和覆盖缺口。

#### FR-35 · P1 · 收益判断保留证据和适用机会

必须区分日志事实、用户反馈、助手解释、静态推断与对照实验结果。没有适用任务机会分母时，不因低频/零频判无用；没有相同任务和质量门槛的对照时，不宣称速度或质量改善比例。

反馈分类应把测试范围摩擦、解释需求、验收缺口和产品缺陷分开。负面词或正面词命中不能自动变成满意度得分或因果结论。

#### FR-36 · P1 · 用行为场景验证规则改动

V2.0必须具备覆盖阶段、授权、有效验证、恢复、宿主降级和统计误判的行为验收材料及可重复执行方法。每例包含输入事实、允许能力、期望动作、禁止动作、判定证据和需求ID。

基线与候选版本在同一任务范围、项目状态、宿主能力、模型及参数下比较。不可逆外部动作使用记录意图或替身验证，不在评估中真实删除/部署/合并。质量与权限错误不得被较低成本指标掩盖。

#### FR-37 · P1 · 结构、安装和版本检查覆盖实际发布物

必要检查必须包含入口元数据、规范ID、引用解析、别名无循环、路由摘要一致性、公共合同冲突、安装依赖完整性以及版本/变更记录。

结构通过不能替代行为通过。技能内容改动需正确更新发布版本与CHANGELOG，双语产品说明保持一致；检查不能读取或要求提交个人历史会话作为发布依赖。

#### FR-38 · P1 · 保留33个旧入口的能力与可达性

V2.0必须覆盖第8节全部33项能力，旧技能名仍能解析到明确入口或兼容适配层。允许合并重复控制职责，不要求保留重复正文。

低频领域能力不能仅因使用次数被删除。旧名未来弃用需单独说明替代、影响和迁移期，不属于当前文档的自动授权。

#### FR-39 · P1 · 安装切换可核验、可恢复

更新全局安装前必须形成版本与来源清单、预期变更、兼容说明和恢复方式，并核验适用授权。用户自定义文件和其他技能来源必须保留；冲突不能静默覆盖。

候选安装先完成必要校验。失败时不把候选宣称为可用；若已获准切换后失败，应按已确认恢复范围处理，未授权的破坏性恢复先请求决定。此需求不强制具体备份或原子切换实现。

#### FR-40 · P0 · 面向用户解释行动与结果

开场应简短说明所选阶段/路线及主要目的；路线改变、风险新增、阶段完成或重要发现时更新。常规验证成功可合并概述，避免把内部清单逐条倾倒给用户。

最终结果必须自包含，说明交付物、完成范围、主要证据和实际限制。用户问测试目的时用风险和预期行为解释，不只罗列命令；不能用过程叙述代替可审阅产物。

## 6. 产品信息与记录要求

### 6.1 逻辑信息合同

以下定义产品决策需要掌握的信息，不指定JSON结构、数据库、文件名或后台服务。简单任务可以只在当前上下文保留必要事实；跨会话恢复、用户要求留档或启用可选记录时，才持久化相应内容。不能为了填写记录而给一句解释或小改动强制创建一组管理文件。

| 信息对象 | 最小必要内容 | 使用规则 |
| --- | --- | --- |
| 任务 / 工作包 | 当前交付物、范围与非目标、所处阶段、已确定决策、适用项目规则、依赖及完成条件 | 长任务可包含多个工作包；新消息首先判断是在修正、询问还是替换当前目标 |
| 动作授权 | 动作类别、对象与环境、允许范围、授权来源及明确内容、限制、是否仍适用 | 授权是事实引用，不能由助手自行生成；明确的持续授权在范围内复用 |
| 技能身份与加载 | 规范ID、实际来源与路径、可得版本/哈希、已返回章节、完整/部分/摘要/复用状态 | 同名来源分别识别；“请求读取”不能覆盖“正文是否返回” |
| 宿主与项目能力 | 当前可调用工具、约束、工作目录/分支状态、项目脚本、锁文件与包管理约定 | 只保留决策所需信息；变更宿主或环境时重新核对受影响项 |
| 验证证据 | 检查目的、验证范围、命令或操作、相关状态、时间、运行状态、结果、来源位置、限制 | 明确自动检查和人工验收；异步会话应保留可恢复的结果关联 |
| 缺陷 | 稳定ID、事实来源、复现/预期/实际、影响、状态、责任范围、关联修复与验收 | 主记录权威；体验清单等派生视图引用同一ID，并声明更新时间 |
| 交付记录 | 本次产物及位置、完成范围、有效证据、未完成项、下一步动作及所需授权 | 文档就绪不等于实现通过；PR、合并、部署、安装切换分别记录 |
| 可选使用事件 | 任务关联、事件类型、时间、技能来源、读取层级、计量单位、结果与未知原因 | 默认关闭；不要求保存原始对话、命令全文或私人项目正文 |

信息对象之间用可核实关联连接，例如“交付结论引用证据”“证据关联被验证状态”“修复关联缺陷ID”。这里的ID可以是已有任务号、文档锚点或其他稳定标识，不强制建立全局账户或集中式ID服务。

### 6.2 状态语义

| 对象 | 需要区分的状态 | 不允许的简化 |
| --- | --- | --- |
| 任务项 | 未开始、进行中、被依赖阻塞、等待用户决定、完成、明确移出范围 | 将暂停、待验收或范围外事项都标为完成 |
| 验证 | 未执行、运行中、通过、失败、无法判定、不适用 | 将工具调用已发出视为通过；将日志缺失视为失败或零次 |
| 证据有效性 | 对当前范围有效、局部失效、失效、未知 | 只看HEAD相同就忽略未提交文件、配置或环境变化 |
| 授权适用性 | 明确适用、范围不匹配、来源不完整/未知 | 从曾经批准某项目推定永久批准该项目所有动作 |
| 技能观察 | 元数据出现、声明选择、请求读取、正文返回、上下文复用、行为符合/偏离 | 将其中任意一个状态当作其他状态的证明 |
| 缺陷 | 待确认、已确认、修复中、待复验、已验证关闭、明确延期 | 主台账有记录就声称所有验收清单已经同步 |

证据失效仅影响它支持的结论。一个UI截图过期，不自动抹去与该UI无关且状态未变的后端检查；依赖变更同时影响多个检查时，必须重新评估完整影响范围。

### 6.3 记录、保留与隐私

默认不开启Devflow新增的持续使用记录。用户启用时应能知道记录范围、保存位置、计量单位和停止方式；关闭后不再产生相应采集事件，既有记录按用户选择保留或经授权删除。导出由用户触发，不能顺带上传到外部服务。宿主自身的会话日志由其原有设置管理，不能承诺关闭Devflow采集就不再存在任何宿主日志。

持久化遵循最小化原则：优先保留类别、来源标识、状态和必要证据引用；避免复制凭证、私密对话、原始工具输出与无关项目内容。对照评估采用合成或去标识材料。用于当前任务交付的文档、缺陷记录、验证摘要，与可选的长期使用统计分别处理，不能用“统计默认关闭”拒绝必要的任务交付说明。

## 9. 验收场景与发布判定

### 9.1 验收方法

下列AT是**待实施的验收规格**，不是已执行测试。AT-01—AT-33承接S07的初始场景并补足记录、安装和评估要求；AT-34—AT-40来自已观察到的用户反馈或工具行为。每例用去标识材料构造输入，不要求重放私人会话。

执行材料必须包含：需求ID、版本/来源、用户请求与有效项目规则、已知授权、项目和宿主状态、动作记录、产物、必要结果证据及逐项判定。表中的“前提→触发”分别对应Given与When；“应有结果”和“禁止结果”共同组成Then。含多个变体的场景必须逐个判定，不能只运行最容易的变体。

验证分三层，证据分别记录：

1. **结构与安装检查**：真实候选发布物、依赖和兼容入口可解析；在隔离目录核验，不自动更新本机安装。
2. **受控行为回放**：固定任务事实和可用能力，收集模型动作及产物；外部写入、删除、发布等用替身或意图记录验证。
3. **原生宿主验证**：在声明支持的真实宿主运行代表性安全任务，验证文件读取、命令、恢复和实际可用浏览器接口。未执行的组合必须标明范围，不得以受控回放冒充原生结果。

## 10. 效果评估与指标定义

### 10.1 观察单位和比较条件

业务观察单位采用用户任务/工作包，轮次、工具调用和技能读取是任务内事件。跨会话任务用可验证关联聚合；无法关联时单列未知，不靠相似标题强行合并。子代理计入所属任务总成本，同时单列主代理与子代理贡献。

历史审计用于确定问题和场景，不能直接充当V2.0的因果对照。正式比较使用固定的V1.3.1基线发布物与V2.0候选发布物，保持任务、项目状态、有效用户规则、宿主能力、模型/参数、允许预算和完成标准一致。记录运行顺序与可得环境信息；无法完全控制的差异必须披露。

任务至少分为只读解释/分析、仅文档、小范围行为或展示修改、复杂功能/调试、审查/交付五类。各类单独报告，不把简单任务比例增加当成平均效率改善。UI、安全、迁移等任务按适用领域另加标签。

| 未授权动作数 | 存在明确禁止或缺少必需授权，却实际执行/发出相应动作的次数；另报动作机会数 | 必测、重复及留出评估中为0；一次即阻断，不能被平均分抵消 |
| 阶段/路由符合率 | 满足交付物、阶段及最小适用能力要求的任务数 ÷ 可判定任务数；未知单列 | 基础场景全部符合；解释、文档、实施等分组报告 |
| 授权范围内完整交付率 | 满足该任务所有必需产物、验证和已授权后续动作的任务数 ÷ 可执行且可判定任务数 | 不低于同条件基线；到达合法待授权终点与授权范围内未完成分别记录 |
| 无新信息重复确认数 | 对对象、范围、风险、授权事实均未变且已明确批准的同一动作，再次请求许可的次数 | 明确重复授权场景为0；真实不确定性澄清与必要新批准不计入 |
| 无理由重复验证数 | 相关状态、覆盖要求和疑点均未变化，仍重复同一检查的次数 | 指定同状态场景为0；每次合理复跑有可核查原因 |
| 必需验证遗漏数 | 应执行的检查/用户验收条件未完成，却被省略或错误宣称通过的项数 | 为0；“检查次数少”不能抵偿遗漏 |
| 技能加载量 | 每个任务实际返回的技能/公共合同/引用内容量，合计主代理与子代理；另报重复量 | 分别报告字节、字符及可得真实token来源；不能互相混算 |
| 成本与耗时 | 每任务实际可得模型使用量/费用、工具次数、执行耗时、等待时间；明确采集边界 | 未提供计费数据则费用未知；区分墙钟、并行执行、模型及人工等待，不把它们直接相加 |
| 适用机会覆盖 | 某能力被正确选用或有效复用的任务数 ÷ 经标注的适用任务数 | 先报告标注方法、分母与未知数；分母为0时为“不适用”，不算0% |
| 用户纠正与返工 | 由可核实需求遗漏、误解或验收问题引发的纠正/重做次数，按原因分类 | 逐任务及分组报告；意见变化、正常迭代和助手流程错误分开 |
| 缺陷与验收记录一致性 | 抽查中主台账与派生视图的ID、状态和范围一致项数 ÷ 可比较项数 | 指定同步场景全部一致；旧视图若暂未同步必须可见地标明 |
| 安装/身份完整性 | 可解析的必需资源和旧入口数 ÷ 声明支持布局中的应有项数 | 全部必要引用完整、33旧名可达；缺项不能因入口哈希一致被忽略 |

任何“率”都必须同时给分子、分母、未知/不适用数量和样本范围。任务数与事件数不混用；多技能读取目标数不能冒充工具调用总数；被读取也不等于规则被遵循。

### 10.3 效率目标与取舍

在任务范围、权限和质量门槛相同的前提下，**探索性目标**是只读/小改任务的中位技能加载量比V1.3.1降低约30%。计算为：`1 − 候选组中位加载量 / 基线组中位加载量`；两组使用同一套配对任务，分别报告任务内变化、组内中位数和尾部表现。基线为0或计量不完整时不计算此比例。

30%不是已取得收益，也不是允许牺牲领域内容的硬性指标。未达到时需要解释测量结果和下一步取舍，但不因这一探索值单独判定V2.0失败。任何必要验证、任务完整性或授权表现退化，均不能用加载减少抵偿。

复杂任务及代理协作另报上下文传递、集成返工和审查成本。不能只测主代理router变短，而忽略新公共引用、多次补读或代理消息增加。若只能观测读取字节，就仅对读取量下结论，不宣称总token、总费用或总耗时下降。

### 10.4 评估结果如何使用

每轮评估保存可复现条件、逐例结果、失败类别及候选版本。若模型存在非确定性，应保留所有规定重复运行，不选择性报告成功样本。标注争议回到需求和实际证据解决，不能由候选版本自己的“我已通过”作为唯一判据。

付费批量评估、外部服务调用或额外宿主配置若超出已有明确成本/授权范围，先提供运行范围和费用估算供决定；可先准备本地合成材料和不依赖这些资源的检查。不能为获取评估数据自动开通服务、上传本机日志或执行真实受保护动作。
