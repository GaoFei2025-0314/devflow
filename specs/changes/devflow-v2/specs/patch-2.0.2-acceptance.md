## 1. 补丁声明与来源冻结

本次可交付的声明仅为“2.0.2 相对 v2.0.1 的变更范围已通过增量验收”。不得由此声明 V2.0 对 V1.3.1 的 40 AT/全部变体、关键重复、十对留出和效果比较全部通过，也不得声称没有可比数据的效率提升。`check-behavior.py verify --profile release` 保持现有 schema、退出码和全量配对语义；`checkpoint` 不能代替补丁发布门槛。

在执行前冻结 `v2.0.1` 到拟交付提交及其工作树的完整文件差异、最终候选发布物清单和来源 SHA-256。加本文前的预备快照 `candidate-final-002` 内容 SHA-256 是 `c1786019b71eb810a5afea83d522682f36ac2879810dde37cc3d113a91bd5911`；它不是最终 2.0.2 来源。产品文件、测试判定或依赖变更后应生成新快照，并逐项复核原证据有效性。不得用 `candidate-final-001`→`candidate-final-002` 的三文件差异代替本次从 `v2.0.1` 起算的补丁范围。

影响表须逐文件对应需求、行为场景和检查，并列出“不影响”的依据。当前范围至少涉及发布结果与证据校验、隔离安装、可观察性规则、身份测例、插件版本和双语说明；最终以冻结差异为准。本补丁清单中的 AT-02/30/31/33 及两条新留出必须在精确的最终候选来源上新运行，不接受旧来源复用。对清单外的历史结果，旧证据复用只能在其实际依赖文件、任务前态、有效规则、模型/参数、宿主所用能力和预算策略仍覆盖当前声明时成立。对 AT-28、AT-29、AT-40 **每个变体** 先判断本补丁是否触及其判定前提；未触及者写“本补丁未重验”，触及者定向重测或明确缩小补丁声明。只有具备有效旧证据重绑定或新运行结果，才可声称当前候选 PASS；不能以一个代表变体或旧候选的来源标签概括全组。

执行前把下表展开为不可事后删减的补丁范围清单：逐变体列 case ID、variant ID、全部预期/禁止 assertion ID、最少独立次数，以及两条封存留出的类别、输入哈希、断言和曝光记录。清单自身的原始字节哈希随发布证据绑定。改名、跳过失败、只选择通过轮次均无效。

最终补丁候选的范围内断言必须全部 PASS，不能有 FAIL、UNKNOWN、未经授权动作或来源不足。三次高风险重复是三次独立有效运行，不是同一轨迹的三份声明。历史基线 FAIL、被污染材料、宿主异常、未知结果和后来的通过都保留在尝试清单中，逐条说明是否计入本轮以及理由。独立评审逐条查看原始轨迹与禁止动作；执行者自己的报告和结构校验退出 0 均不能代替语义判断。

## 3. 补丁证据与校验器

补丁使用单独命名的 `verify --profile patch` 与补丁范围清单。范围清单绑定最终候选 SHA、逐变体断言/重复和两条封存留出。每个 case 记录该案例规范化 JSON 的 `case_sha256`，每条留出记录冻结的评审准则文件原始字节 `rubric_sha256`；后者是独立评审材料，**不是执行者的宿主捕获**。schema 2 发布清单绑定范围清单原始字节哈希、派发前的 `scope_seal`、协调者编制的尝试台账、实际捕获及结果文件哈希，并为留出提供证据根内的 rubric 路径/哈希以核对。每次普通候选与留出运行都要有宿主捕获的实际派发输入及接收事件；封存输入和 rubric 分别作为作者材料，不能伪称宿主捕获。AT-33 完整安装的三次运行须有不同 actor、原生调用、原始轨迹、派发和接收身份，独立评审再核对真实性。检查器应拒绝范围缺项、重复身份、错误源码、哈希不符、声明冒充宿主捕获、不同名同证据、额外未登记的成功记录、合成夹具冒充发布证据，以及未满足重复或留出要求。补丁档退出 0 只说明**2.0.2 增量证据结构完备**；全量 `release` 的退出 0 和独立语义评审仍分别是不同结论。

每条有效运行保存实际任务输入、初始文件字节或哈希、有效规则、实际模型及参数、预算策略、宿主与 CLI、派发原文及接收事件、命令/工具返回、状态变更、加载覆盖、原生轨迹和独立判定。分阶段审批必须在候选评估后，通过真实宿主消息通道把目标、候选和恢复范围明确送达；材料中写着“未来会批准”不能算批准。原始记录不覆盖；格式补证另建清单，注明原哈希、字段差异和逐项来源，不改执行身份与原判定。

无需把 V1.3.1 每一场景再配对跑一次才能判定 2.0.2 补丁；`v2.0.1` 可用于变更回归参考，但补丁门槛是最终候选在上述风险路径上的真实行为与安装结果。涉及效果或相对改善的量化主张另须可比配对数据，不能从补丁档推导。

## 4. 宿主和安装的最小核验

Windows Codex 为本补丁主要原生环境。先各做一个 AT-02 与 AT-33 采集预检，证明原始输入、前态、实际接收、工具结果和审批事件可追溯；预检不完整时先修采集链路。每次原生运行记录入口及退出的完整工具注册表、实际使用的工具及调用、脱敏的相关配置投影与哈希、CLI 版本、模型、权限、预算和有效规则。

与场景无关、在运行后才出现的 iOS 工具，可在证明原有条目未变且未被使用的前提下标为宿主背景变化；它本身不是 Devflow 规则失败。模型/参数、权限、**被用工具**、有效规则、任务结果或审批通道发生影响判定的变化时，该轮仍须判为不可比或 UNKNOWN/FAIL 并定位。仅有全局配置总哈希、没有前后内容证据的旧 AT-14 尝试不能倒推为有效。能否计入补丁只看当前候选的原生合同与实际证据，不用“工具全集必须与 V1.3.1 相同”作前提。

隔离目录内对最终候选分别验证完整包、单技能及声明依赖闭包、真实链接安装；检查发布文件实际内容、引用可达性、版本及冲突/恢复行为。Claude Code 保持入口格式及受控合同口径；Cursor 原生验收仍延期且公开状态不得写为通过。不得借补丁验收切换本机全局安装。

## 5. 收尾判定

离线检查至少包括 `scripts/check-refs.sh`、`scripts/check-bundle.py`、Windows 与 Ubuntu 适用的维护测试、40 AT/66 变体材料 `validate`、`git diff --check` 及涉及拒绝路径的负向测试。有效且未受影响的同来源结果可引用，不因新一轮会话机械重跑。最终还需来源/隐私扫描、完整历史处置、独立语义审查、补丁校验退出 0、可审 PR 与必需 CI。若任一补丁必测项或证据门槛未完成，应写“2.0.2 增量验收未完成”，不能改用 `checkpoint` 或删场景获得通过。风险变更合并另需用户明确批准；标签发布、全局安装切换、分支删除分别走各自授权。
